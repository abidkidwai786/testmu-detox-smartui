## How the SmartUI integration works

| File | Role |
|------|------|
| [`e2e/smartui.ts`](e2e/smartui.ts) | `visualSnapshot(name)` helper — captures a screenshot via Detox and copies it to a deterministic `smartui-screenshots/` folder. Gated by the `VISUAL` env var; tags filenames with `SMARTUI_DEVICE_TAG`. |
| [`e2e/suite1.test.ts`](e2e/suite1.test.ts), [`e2e/suite2.test.ts`](e2e/suite2.test.ts) | Call `visualSnapshot('...')` after each assertion. |
| [`detox.config.js`](detox.config.js) | Screenshot artifact plugin set to `'all'` when `VISUAL` is set (so passing-test screenshots are kept). |
| [`lambdatest/scripts/smartui-upload.sh`](lambdatest/scripts/smartui-upload.sh) | Post-test step: boots Node via nvm and runs `npx smartui upload` with a **unique build name**. |
| [`yaml/hypexRDAndroid.yaml`](yaml/hypexRDAndroid.yaml) | HyperExecute config: pins the device, sets `VISUAL`/`SMARTUI_DEVICE_TAG`, injects `PROJECT_TOKEN`, and adds the `post:` upload step. |
| [`.smartui.json`](.smartui.json) | SmartUI CLI config (generated by `smartui config:create`). |

**The design choice that matters:** `device.takeScreenshot(name)` returns the temp path of the captured image. The helper copies it out *immediately* into `smartui-screenshots/`, so we never have to scrape Detox's timestamped `artifacts/` folders, and the capture is independent of the plugin's keep/discard policy.

```ts
// e2e/smartui.ts (core)
export async function visualSnapshot(name: string): Promise<void> {
  if (!process.env.VISUAL) return;                 // no-op on normal runs
  const tempPath = await device.takeScreenshot(name);
  fs.mkdirSync(OUT_DIR, { recursive: true });
  const tag = process.env.SMARTUI_DEVICE_TAG || '';
  const fileName = tag ? `${name}-${tag}.png` : `${name}.png`;
  fs.copyFileSync(tempPath, path.join(OUT_DIR, fileName));
}
```

## Step-by-step: add SmartUI to a Detox suite

### 1. Create a SmartUI project

In the SmartUI dashboard, create a project of type **Uploads / CLI** and copy its **Project Token** (format: `orgId#projectId#ProjectName`).

### 2. Install the SmartUI CLI

```bash
npm install --save-dev @lambdatest/smartui-cli
```

> Requires Node.js ≥ 20.3 (CLI 4.x). This repo pins Node 20 via [`.nvmrc`](.nvmrc).

### 3. Create the config

```bash
npx smartui config:create .smartui.json
```

### 4. Capture screenshots in your tests

Add the helper and call it where you want a visual checkpoint:

```ts
import { visualSnapshot } from './smartui';

it('should have welcome screen', async () => {
  await expect(element(by.id('welcome'))).toBeVisible();
  await visualSnapshot('welcome-screen');
});
```

### 5. Keep passing-test screenshots

In `detox.config.js`, make sure the screenshot plugin keeps artifacts during a visual run:

```js
artifacts: {
  plugins: {
    screenshot: process.env.VISUAL ? 'all' : (process.env.CI ? 'failing' : undefined),
  },
},
```

### 6. Upload after the run

```bash
export PROJECT_TOKEN="orgId#projectId#ProjectName"
VISUAL=true npm run test:lambdatest-android    # capture
npx smartui upload ./smartui-screenshots --buildName "my-build-$(date -u +%Y%m%d-%H%M%S)"
```

The **first** upload creates the baseline; later uploads are compared against it.

## Run it on HyperExecute

### 1. Set credentials

```bash
export LT_USERNAME="YOUR_USERNAME"
export LT_ACCESS_KEY="YOUR_ACCESS_KEY"
```

### 2. Provide the SmartUI token as a secret (never commit it)

The YAML references the token as `${{.secrets.PROJECT_TOKEN}}`. Supply the value through a **job secret file** kept outside the repo:

```bash
printf 'PROJECT_TOKEN=orgId#projectId#ProjectName\n' > /tmp/smartui.secrets
```

### 3. Launch the Android real-device job

```bash
./hyperexecute --config yaml/hypexRDAndroid.yaml --job-secret-file /tmp/smartui.secrets
```

> ⚠️ **Always pass `--job-secret-file`, including with `--validate`.** `${{.secrets.*}}` is resolved against the secret vault, so validating/running without the file fails with `Secret Key PROJECT_TOKEN not found in vault`.

The job: provisions the pinned device → builds/runs the Detox tests with `VISUAL=true` → the `post:` step uploads the screenshots to SmartUI. View the result on the SmartUI dashboard.

## How a comparison build works

SmartUI compares each screenshot **by name** against the baseline build of the branch.

- **Build #1** (first upload) → becomes the **baseline**, auto-approved.
- **Build #2** (a later upload with a **different build name**) → each screenshot is diffed against the baseline; if anything changed the build goes to **`pending-approval`** with a per-screenshot mismatch %.

> 🔑 **Each run must use a UNIQUE build name.** If you re-use a build name, SmartUI maps the upload onto that *same* build and overwrites it in place — **no comparison is produced**. [`smartui-upload.sh`](lambdatest/scripts/smartui-upload.sh) appends a UTC timestamp to guarantee uniqueness:
>
> ```bash
> BUILD_NAME="${SMARTUI_BUILD_NAME:-LT-Detox-RD-Android}-$(date -u +%Y%m%d-%H%M%S)"
> ```

## Important limitations & gotchas

These come from the Detox + SmartUI image-upload model (and from building this repo):

1. **No device metadata on uploads.** Pin **one device model per project**, or encode the model in the filename (this repo does both: device pinned to `Pixel 7-13` *and* `SMARTUI_DEVICE_TAG=pixel7-android13`). A wildcard like `.*-13` lets different hardware/resolutions run, causing false diffs.
2. **Status bar causes false positives.** The clock/battery change every run (a ~0.03% mismatch on every screen). Configure an **ignore region** over the status bar in the SmartUI project settings.
3. **No DOM-based Root Cause Analysis / Layout mode.** Detox uploads plain images, so these DOM-dependent SmartUI features are unavailable.
4. **HyperExecute real devices: Android only** for Detox. (The iOS *simulator* flow on a Mac VM can also upload images.)
5. **This sample runs a prebuilt APK — there is no build step.** `detox test` only *runs* the APK committed under `android/app/build/...`; editing `app.js` has **no effect** until the APK is rebuilt (`npm run build:android-release`, or add a `detox build` step to the HyperExecute `pre:`/flow). If a source change doesn't show up in the diff, this is why.

## Running the base Detox suite

### Prerequisites

- Node.js and npm (this repo targets Node 20 via `.nvmrc`)
- HyperExecute CLI binary ([download](https://www.testmuai.com/support/docs/getting-started-with-hyperexecute/))
- A TestMu AI account (username + access key)

### Install

```bash
npm install
```

### The three sample YAMLs

```bash
# iOS simulator
./hyperexecute --user $LT_USERNAME --key $LT_ACCESS_KEY --config yaml/hypexSim.yaml

# Android real device (SmartUI enabled)
./hyperexecute --user $LT_USERNAME --key $LT_ACCESS_KEY --config yaml/hypexRDAndroid.yaml --job-secret-file /tmp/smartui.secrets

# Android parallel (autosplit)
./hyperexecute --user $LT_USERNAME --key $LT_ACCESS_KEY --config yaml/hyperexecuteParallel.yaml
```

### Local testing with TestMu AI Tunnel

To test locally hosted apps, set up the tunnel ([Windows](https://www.testmuai.com/support/docs/local-testing-for-windows/) · [macOS](https://www.testmuai.com/support/docs/local-testing-for-macos/) · [Linux](https://www.testmuai.com/support/docs/local-testing-for-linux/)) and add `tunnel: true` to your capabilities.
